## まず知っておきたい現在地

再構築は、**CIの安定化を終え、現行環境とデータの棚卸しを進めている段階**です。

CIをNode.js 26へ統一し、GitHub ActionsのNode.js 20警告を解消した作業は完了しています。公開インフラと公開経路から見えるRoomデータの調査も一部完了しました。再構築要件、データモデル、APIの設計案は文書化されています。一方、本番AWSアカウントを直接調べる権限がなく、S3全データの確認、正式なバックアップと復元確認、利用状況・本番費用の把握は終わっていません。新環境の構築や新Web/APIの実装は未着手です。

そのため、現時点では全体の完了率やリリース日を根拠をもって示せません。まず本番環境の読み取り調査を完了し、基盤と移行方法を決めてから実装計画を確定するのが妥当です。

## 棚卸しで確認できたこと

- 本番WebはCloudFront経由でS3の静的ファイルを配信し、GitHub ActionsからOIDCでデプロイされています。
- 現行WebはバックエンドAPIを使わず、CloudFront経由でRoom JSON等を直接読み書きします。
- 公開索引にはRoomが10件あり、そのうち8件を取得でき、2件はHTTP 403でした。これは索引から到達できた範囲の数であり、全データ件数ではありません。
- 取得できた8件では、ID形式の不一致が1件、ホスト参照の不整合が1件見つかっています。移行時に自動修正せず、確認対象にする方針です。
- 本番AWSアカウントとローカルAWS CLIのアカウントが異なるため、本番S3の全件一覧や本番の監視・請求情報を確認できていません。
- 新しいAPIのOpenAPI仕様案はあり、認証、Room単位の権限、再送対策、競合検知を含む設計が書かれています。これは実装済みを意味しません。

詳細は[現行インフラ棚卸し](current-infrastructure.md)、[現行データ棚卸し](data-inventory.md)、[再構築計画](rebuild-plan.md)を参照してください。

## 先に解消する課題

1. **本番AWSの読み取り権限がない** — 監査用ReadOnlyロールを用意し、本番アカウントのリソース、S3オブジェクトと過去Version、CloudWatch、費用を確認する必要があります。
2. **正式なバックアップと復元が未検証** — 現行バケットを変更せずにスナップショットを作り、別の場所へ復元して照合する必要があります。
3. **Roomデータに要確認項目がある** — 取得できない2件、Room ID形式不一致、ホスト参照不整合を、原本のVersion情報とともに確認する必要があります。
4. **現行経路には認証付きのRoom単位アクセス制御がない** — 再構築版の認証・認可ができるまでは現行サービスを維持し、移行時に新経路へ安全に切り替える必要があります。

## 今後の進め方

### 次に行うこと

1. 本番AWSの監査用読み取りアクセスを確保する。
2. S3全体とVersionを一覧化し、Room・User・孤立オブジェクトを含む正式なデータ量を記録する。
3. 暗号化したスナップショットを別の保存先に作成し、検証用の場所へ復元して件数・内容を照合する。
4. CloudWatchからアクセス・エラー状況を、Cost Explorerから直近の費用を確認する。
5. これらを踏まえて段階0を完了し、基盤費用と運用方式を比較する。

### その後の順序

1. API境界、Googleログイン、MySQLの運用先、リアルタイム同期、Room権限、移行・切り戻し基準を決定する。
2. ステージングを含む新環境とCI/CD、監視、バックアップを構築する。
3. Web/APIを並行開発し、ステージングで主要な利用フローと同期・障害時の動作を確認する。
4. スナップショットを使って移行リハーサルと復元を行い、不一致や再実行を確認する。
5. テストRoomから限定切替し、問題がなければRoom単位で段階的に拡大する。
