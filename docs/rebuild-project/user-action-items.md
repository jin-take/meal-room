# MealRoom 再構築 ユーザー作業一覧

更新日: 2026-11-08

この文書は、PMやrebuild-childだけでは進められない準備と、ユーザーに判断してもらう事項をまとめます。進捗の正本は[再構築ステータス](rebuild-status.md)です。

## まずお願いしたいこと

### 1. childへ作業指示を渡す

[rebuild-child 作業指示](rebuild-child-instructions.md)を`rebuild-child`のスレッドへ貼り付けて、選択肢比較資料の作成を依頼してください。こちらから別スレッドへ直接メッセージを送ることはできないため、これがchildの作業開始に必要です。

### 2. 本番AWSの読み取り専用アクセスを用意する

フェーズ1の残作業を完了するには、GitHub Actionsがデプロイしている本番AWSアカウントを読み取れる必要があります。アカウント管理者またはAWS管理担当者へ、次の条件で監査用アクセスを依頼してください。

- `AssumeRole`またはAWS IAM Identity Centerによる短期認証を使う。
- 対象は本番アカウント内の棚卸しに必要な読み取り操作に限る。少なくともS3と全Version、CloudFront、Route 53、ACM、CloudFormation、Lambda、API Gateway、RDS、CloudWatch、Cost Explorer/Budgets、GitHub OIDCデプロイロールの設定確認を含める。
- S3への書き込み・削除、IAM変更、DNS変更、CloudFront更新、CloudFormation変更、デプロイ権限は付与しない。
- ロールARNと利用方法を安全な方法で共有し、アクセスキーやシークレットをリポジトリ、チャット、ドキュメントへ貼らない。

アクセスを用意したら、ローカルAWS CLIで対象の本番アカウントを選択できるようにし、`aws sts get-caller-identity`で想定アカウントのロールを引き受けられることを確認してください。アカウント番号やARNは公開資料へ記録せず、棚卸し結果には必要なリソース名と確認結果だけを残します。

## childの比較資料を確認した後に決めること

以下は設計・費用調査の結果を見て決定します。根拠がそろう前に、急いで選ぶ必要はありません。

| 判断事項 | 決める内容 |
| --- | --- |
| Room権限 | 招待、メンバー削除、host移譲、退室、Room削除を誰が実行できるか |
| 旧メンバーの引き継ぎ | Googleログイン後、既存端末・Roomメンバーをどの確認方法で結び付けるか |
| 同期体験 | 目標とする変更反映時間、通信断時に未送信変更をどう見せるか、どの程度の月額を許容するか |
| MySQL運用 | 可用性・バックアップ要件と月額上限。実利用数と費用比較を見て選ぶ |
| Room切替 | 限定切替の観測期間、許容エラー率、切り戻し期限、サポート窓口 |
| 広告 | Google Adsの出稿かサイト内広告掲載か。優先度は低いため、後回しも選択可能 |

## 現時点で保留してよいこと

- 日付入りの公開予定。AWSアクセス、費用、未決事項、実装見積もりをそろえてから設定します。
- Roomの本番移行や現行S3データの削除・変更。バックアップ、復元、移行手順の実証前には行いません。
- 広告方式の決定。主要機能と安全な段階移行を優先します。

## 完了・共有のしかた

AWSアクセスの準備状況と判断結果は、[再構築ステータス](rebuild-status.md)の担当・ブロッカー・決定事項へ記録してください。認証情報は記録せず、「監査用ロールを利用可能」「どの棚卸し範囲を確認できるか」のように状態だけを残します。
