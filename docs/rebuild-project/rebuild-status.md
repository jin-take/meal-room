## フェーズ1: 現行環境とデータの棚卸し

### 実施済み

- `meal-room.link`がCloudFrontとS3から配信されていることを確認
- GitHub ActionsがOIDCで本番AWSロールを引き受けていることを確認
- 本番WebのS3バケット名、CloudFront Distribution ID、リージョンを確認
- Route 53の公開ネームサーバーを確認
- 現行TLS証明書が`meal-room.link`のみを対象としていることを確認
- 予定している本番・ステージング用サブドメインが未作成であることを確認
- 公開応答からS3のAES256暗号化とVersion IDを確認
- CloudFront経由でRoomデータへのGET/HEAD/PUTがCORS許可されていることを確認
- `rooms/index.json`と索引から到達可能なRoom JSONを読み取り専用で検証
- 利用者データの原本をリポジトリへ保存せず、監査用一時ファイルを削除

### 未完了

- S3の全オブジェクト数、全容量、全Version
- `users/*.json`の件数、容量、重複device ID
- 索引にない孤立Room JSON
- バケットポリシー、Public Access Block、OAC、ライフサイクルの実設定
- CloudFrontの全Behavior、アクセスログ、WAF
- 本番AWS内のLambda、API Gateway、RDS、CloudFormation
- CloudWatchのアクセス数、エラー率、転送量
- 本番AWSの月額費用、Budget、異常検知
- GitHub OIDCロールの権限内容
- Version IDを含む正式スナップショット
- 別バケットへの復元試験

### ブロッカー

ローカルAWS CLIのIAMユーザーと、GitHub Actionsがデプロイする本番AWSアカウントが異なります。ローカルユーザーから本番S3は`403 Forbidden`、既知のCloudFront Distribution IDは`NoSuchDistribution`になります。

本フェーズを完了するには、本番AWSアカウントへAssumeRoleできる監査用ReadOnlyロールが必要です。監査ロールに書き込み権限は付与しません。

### 残りの実行順

1. 本番AWSアカウントに監査用ReadOnlyロールを用意する。
2. S3のObject Versionを含む全量マニフェストを取得する。
3. CloudFront、Route 53、ACM、IAM、CloudWatch、稼働サービスを列挙する。
4. 過去3か月の本番費用とサービス別内訳を記録する。
5. 現行S3を変更せず、非公開のスナップショット先へコピーする。
6. 件数、サイズ、Version ID、ETagまたはチェックサムを照合する。
7. 別の検証用バケットへ復元し、全Room JSONを検証する。
8. 棚卸し文書と本書を更新し、フェーズ1を完了へ変更する。

## フェーズ2以降の実行計画

### 2. 未決事項とADR

Google OIDCと内部User UUID、Room権限、RDS MySQL、更新Versionと競合、リアルタイム通知、Room単位の切替・切り戻しを決定記録として残します。

### 3〜4. 基盤・DB

本番と分離したステージングをIaCで作り、Lambda、API Gateway、MySQL、Secrets Manager、ログ、アラート、バックアップを構築します。続いてRoom論理分離を持つMySQLスキーマと、S3 JSONからの再実行可能な移行ツールを作ります。

### 5〜7. 認証・API

Googleログインと`/me`を最初に完成させ、Room権限API、レシピ、献立、買い物の順に実装します。更新はPOSTを基本に、入力検証、Room認可、冪等性キー、期待Version、トランザクション、監査ログを必須とします。

### 8〜9. Web・同期

既存Webへ`LegacyS3Repository`と`NewApiRepository`の切替層を設け、Room単位のFeature Flagで段階接続します。まずGETで正しい状態を復元できるようにし、その後で更新通知、未送信キュー、再送、再接続を追加します。

### 10〜12. 移行・公開

正式スナップショットから移行をリハーサルし、開発用Room、自分のRoom、協力者Room、少数の一般Roomの順に切り替えます。旧S3データは保管期限まで保持します。サービスページは`web/`内の別成果物として`home.meal-room.link`へ公開します。

## リスク

| 優先度 | リスク | 状態・対応 |
| --- | --- | --- |
| 必須 | 本番AWSの監査権限がなく、完全な棚卸しと復元試験ができない | 監査用ReadOnlyロール待ち |
| 必須 | 現行CloudFront経由で認証なしPUTが許可される | 新API安定まで維持し、Room単位移行後に閉じる |
| 必須 | 索引10件のうち2件のRoom JSONを取得できない | S3 Version一覧で実体と削除履歴を確認する |
| 高 | `hostMemberId`不整合が1件ある | 自動修正せず移行時の確認対象にする |
| 高 | Room ID形式が異なるデータが1件ある | 旧IDと新UUIDの対応表を保持する |
| 高 | 現行証明書がルートドメインのみ | サブドメイン用証明書をIaCで作る |
| 中 | mainから本番Webへ直接デプロイされる | ステージング自動、本番承認へ分離する |

## 更新ルール

1. 作業開始時に対象フェーズと担当行を`進行中`へ更新する。
2. 作業完了時に成果物、検証結果、残作業、リスクを更新する。
3. 推測を完了扱いにせず、確認できた事実と未確認項目を分ける。
4. 本番変更、移行、削除は実行前に切り戻し方法を記録する。
5. API、要件、データモデルを変更した場合は関連文書も同じPRで更新する。
6. 会話やIssueだけに依存せず、次の担当者が本書から再開できる状態を保つ。
