# MealRoom 再構築計画

更新日: 2026-11-08

## 目的

Web版を先に、既存利用者と既存データへの影響を抑えて段階的に再構築する。現在の公開サービスを止めず、新しいWeb体験とバックエンドを並行して用意し、検証済みのRoomから順次切り替えられるようにする。

本書は現時点の計画と合意済み要件をまとめる。AWSアカウント上の実リソース、利用者数、トラフィック、データ量、請求額は未調査であり、基盤選定前に確認する。

## 合意済み要件と優先度

| 項目 | 要件 | 優先度 |
| --- | --- | --- |

| バックエンド | クライアントからS3へ直接書き込む方式を段階的に置き換える。`api.meal-room.link/...`で公開し、GETとPOSTを基本にする。ECSは採用せず、Lambdaを第一候補にする。 | 高 |
| データ基盤 | 現行S3データを保持し、MySQLを新しい業務データベースとして使用する。S3とMySQLの責務を分け、低コストな運用方式を選ぶ。 | 高 |
| Room構成 | ユーザーは複数Roomへ参加できる。レシピ、献立、買い物リストをRoom単位で分離し、Room所属をアクセス制御の基準にする。 | 高 |

| 同期 | 手動同期と定期ポーリング中心の処理を見直す。更新の即時反映、競合検知、再接続、未送信変更の保護を設計する。 | 高 |

| 広告 | WebへのGoogle広告関連機能を検討する。広告出稿か広告掲載・収益化かを要件確定前に区別する。 | 低 |

## 現状の基準線

- 公開URL `https://meal-room.link/` はReactアプリを配信する。紹介専用ページは`https://home.meal-room.link/`に新設する。
- WebはS3・CloudFront経由で静的配信され、Room JSON、ユーザー設定、Room索引も同じ配信経路からS3へ直接読み書きする。
- Webの更新は3秒ごとのGETと画面フォーカス時のGET、および利用者が押す同期操作で行う。同期時は差分を統合するが、同時PUTを保存時に排他する仕組みはない。
- `backend/template.yaml`にはAPI Gateway/Lambdaが定義され、`backend/src/handler.ts`には旧GET/POST/PUT APIがある。Webの`api.ts`はそれを利用していない。ECS・RDSの定義はリポジトリにない。
- GitHub ActionsにはWebのビルド・テストとCloudFrontデプロイがある。バックエンドのCI/CDはない。
- 現行画面にはRoom、レシピ、献立、買い物リスト、同期、Room設定などがある。レシピ画面やRoom設定の一部はViteプラグインでビルド時に`App.tsx`を書き換えているため、再構築では機能を通常のソースコードへ統合する。
- Flutterシェルは存在するが、今回の公開対象としてはWebを優先する。

現行の保存形式とAPI経路の詳細は[データ設計](data-model.md)と[現行データアクセス仕様](api.md)を参照する。

## 移行方針

### 変更しない原則

1. 現行Webと既存データを、後継システムの検証が終わる前に停止・削除しない。
2. 既存のS3オブジェクトを移行作業で上書き・削除しない。移行前に一覧・件数・サイズを記録し、復元可能なバックアップを取得する。
3. 新Web/API/DBは別のURLまたは環境に配置し、内部検証と少数のテストRoomから開始する。
4. Room単位で移行状態、元データ識別子、移行先識別子、照合結果を記録する。
5. 旧環境と新環境への無条件な二重書き込みは避ける。二重書きが必要なら再送・重複排除・不一致修復の方式を先に設計する。
6. 切替条件を満たさないRoomは旧経路に残す。切替後も一定期間は旧データを保持し、切り戻し可能な期限を設ける。

### 段階

| 段階 | 作業 | 完了条件 |
| --- | --- | --- |
| 0. 棚卸し | AWS実リソース、独自ドメイン/DNS、S3オブジェクト、Room件数、アクセス頻度、CloudFront/API費用、現在の利用機能を確認。現行データを読み取り専用でスナップショット化する。 | 移行対象一覧、データ量、復元手順、基準費用が記録される。 |
| 1. 仕様・基盤決定 | Web導線、API境界、認証の段階、リアルタイム方式、MySQLの運用先、GET/POST契約、Room権限、広告要件を決定する。低負荷時の月額と増加時の費用を比較する。 | ADRまたは決定記録、API仕様、データ移行マッピング、費用見積もりがレビュー済み。 |
| 2. 新環境の土台 | 開発/ステージング/本番を分離し、GitHub Actions、IaC、シークレット管理、ログ・メトリクス・アラート、DBバックアップを設定する。 | Web/APIを本番データへ接続せずにデプロイ・復元確認できる。 |
| 3. WebとAPIの並行開発 | 紹介ページとWebアプリを整備し、Google OIDC、新API、MySQLへ接続する。旧アプリは継続提供し、Google主体と既存Roomメンバーの紐付けを利用者ごとに確認する。 | ステージングでログイン、主要ユーザーフロー、同期、障害時の再試行を確認できる。 |
| 4. 移行リハーサル | S3のコピーから移行ツールを実行し、移行前後のRoom・メンバー・レシピ・献立・買い物項目を件数と内容で照合する。失敗・再実行・復元も試す。 | 再実行可能で、未移行・不一致データを一覧化でき、復元手順が実証される。 |
| 5. 限定切替 | テストRoomと希望する少数Roomだけを切り替える。旧経路を残し、エラー率・同期遅延・DB負荷・費用を観測する。 | 定めた期間、データ欠損・重大障害がなく、切り戻し手順を使える。 |
| 6. 段階拡大 | 問題がない単位から移行し、各段階で照合する。全体切替後も旧データを保管期限まで保持する。 | 全対象Roomが照合済みで、保管・削除判断が承認される。 |

段階0の公開経路と到達可能なRoomデータの棚卸しは2026-11-08に実施した。本番AWSアカウントの監査権限がないため、S3全量、利用者JSON、CloudWatch、費用、正式なバックアップと復元試験は未完了である。詳細と残作業は[現行インフラ棚卸し](current-infrastructure.md)および[現行データ棚卸し](data-inventory.md)を参照する。

### 切替・切り戻しで決める値

実装着手前に、許容するデータ差分（原則0件）、同期反映時間、APIエラー率、観測期間、移行単位、切り戻し期限、サポート窓口を数値または手順で定義する。初期の本番移行では全量一括切替を行わない。

## UserとRoomのデータ分離

### 概念モデル

MealRoomではRoomを共有単位とする。ユーザーは複数Roomへ参加でき、各Roomにメンバー、献立、レシピ、買い物項目を所属させる。

```text
User
  └─ Room memberships (host / member)
       └─ Room
            ├─ Recipes
            ├─ Meal plans
            └─ Shopping items
```

一つのMySQLデータベースを全Roomで共有し、`users`、`rooms`、`room_members`を分ける。レシピ、献立、買い物項目など全てのRoom配下データに`room_id`を持たせる。APIは認証されたユーザーの`room_members`を毎リクエスト確認し、異なるRoomのID混入を外部キーや複合制約でも防ぐ。

Roomごとにデータベースやスキーマを作成する方式は、接続、マイグレーション、監視、費用が増えるため現段階では採用しない。Room単位の論理分離により、低コストな単一MySQL運用と複数Roomへの参加を両立する。

アクセス権は現行仕様に合わせて`host`と`member`を基本とする。ホスト専用操作、ホスト移譲、退室、Room削除の詳細はAPI実装前に確定する。

## GoogleログインとUser UUID

ログイン方法はGoogle OIDCによる「Googleでログイン」だけを提供する。一般GmailとGoogle Workspaceアカウントを対象とし、SAMLは使用しない。Authorization Code + PKCE、`state`、`nonce`を使い、必要なスコープは`openid email profile`に限定する。

MySQLでは`users`にMealRoom内部UUIDを保存し、`user_identities`に`provider: google`とGoogleの`sub`を保存する。`UNIQUE(provider, provider_subject)`で一つのGoogle主体を一つのUserへ結び付ける。メールアドレスは変更される可能性があるため、本人識別や既存ユーザーの自動統合には使用しない。

Webは短期アクセストークンをメモリで扱い、localStorageへ保存しない。更新トークンは`Secure; HttpOnly; SameSite=Lax`のCookieでローテーションする。Cookieを使うトークン更新とログアウトではOriginを検証する。

既存Roomの移行時は、名前やメールアドレスだけで既存メンバーへ自動接続しない。初回Googleログイン後、既存端末の移行用証明、Room招待、またはホスト承認によって内部User UUIDと旧member IDを一度だけ紐付ける。

## 低コスト基盤の比較方針

ECSは採用しない。APIはAPI Gateway + Lambdaを第一候補とし、`api.meal-room.link/...`で提供する。業務データはMySQLに保存し、現行S3はWeb静的ファイル、移行元の保管、バックアップ/エクスポートなど用途を分けて保持する。S3を新データの第二の書き込み先にはしない。

MySQLの運用先は、AWSのマネージドMySQL（RDS等）を基本候補として、想定利用者数・Room数・同時接続・同期頻度に基づき最小構成の月額とバックアップ/可用性費用を見積もる。FirebaseはMySQLを業務データの正とする要件とは異なるため、今回の主要DB候補から外す。Google OIDCはCognito等の認証基盤で仲介し、MySQLにはMealRoom内部UserとGoogleの`sub`の対応を保持する。

リアルタイム方式は、Lambda/APIとMySQLの構成で実現可能な通知方式と、再接続時にGETで整合を回復する方式を比較する。小規模運用では高価な常時接続基盤を急いで導入せず、まず更新イベント・バージョン管理・競合処理を固める。

## Web・同期・APIの設計要件

- まずWebブラウザで完結する体験を完成させる。アプリ内データ画面、紹介ページ、利用開始導線、スマートフォン/デスクトップ対応を設計する。
- サービスページも`web/`に含める。Webアプリとサービスページは別のエントリーポイント・ビルド成果物として管理し、`meal-room.link`と`home.meal-room.link`へ個別に配信する。共通のブランド素材やUI部品は`web/`内で共有する。
- データ更新APIはGET/POSTを基本とし、`api.meal-room.link/...`で提供する。POST更新には重複送信対策、期待バージョンまたは同等の競合検知、サーバー側入力検証、Room単位の権限確認を定義する。
- リアルタイム性は配信方式ごとに費用・遅延・再接続を比べる。プッシュ方式を採る場合も、再接続時のGETによる整合回復を用意する。
- オフラインまたは通信失敗時の未送信変更を保護し、競合時は自動上書きせず、再試行または利用者が判断できる状態を示す。
- 旧S3直結経路は新方式の安定とRoom単位の移行完了まで残す。新旧のAPI/データ形式は本書とAPI文書で区別する。

## GitHub Actionsの目標

- Pull Request: Web/APIの依存解決、型検査、ユニットテスト、ビルド、IaC検証を実行する。
- main: まずステージングへ自動デプロイし、スモーク確認後に本番へ昇格できるようにする。
- 本番: GitHub OIDCを使い、環境単位の最小権限を付ける。シークレットをリポジトリへ直書きしない。
- DBスキーマ変更とデータ移行はアプリの自動デプロイから分け、バックアップ・互換性確認・ロールバック方法を伴わせる。
- 現行Webのデプロイを維持したまま、新APIのCI/CDを別ワークフローまたは環境として追加する。
